# 권한과 데이터 보호

## 개인 프로젝트와 로그인 저장

각 교사가 자기 Supabase 프로젝트에 연결합니다. Google 비밀번호는 Google, 사용자 UUID·이메일·인증 프로필은 해당 프로젝트 Auth, 로그인 유지 토큰은 브라우저 SDK 저장소에 있습니다. 배포자 공용 회원 DB는 구현하지 않았습니다. 교사 연결 URL·공개 키도 현재 브라우저에 저장하고 번들에 기본 프로젝트를 넣지 않습니다. 공통 웹 코드는 세션으로 동작하므로 배포 계정·의존성·XSS 보안은 여전히 배포자의 책임입니다. 각 교사는 계정·RLS·비밀키·학생 데이터 보존을 관리합니다. 자세한 분담은 SETUP.ko.md 9~10절을 참고하세요.

## 강제하는 경계

- 최고 관리자는 `app_admins`의 Auth UUID 한 명이다. 생성 시 행은 0개다. 가입 트리거·최초 로그인 자동 승격·이메일 비교 권한 부여는 없다.
- ③ 소유자 SQL과 ④ 보안 SQL을 적용한 현재 버전에서는 Google 인증과 SQL Editor에서 지정한 소유자 UUID가 모두 일치해야 자기 app_teachers 행을 생성할 수 있다. 이전 공용 프로젝트 회원 행이 남아 있어도 소유자가 아니면 app_is_teacher()가 false다. 다른 계정의 이용 상태를 바꾸거나 최고 관리자가 될 수 없다. 데이터 접근은 active 교사 + app_classes.owner_id와 auth.uid() 일치 조건이다. 학생·기록·명령·캡처·최신 명령 view·Storage·Realtime에 같은 소유권 RLS를 적용한다. 직접 테이블 쓰기는 허용하지 않는다.
- 교사 브라우저의 DB 쓰기는 입력을 제한한 교사 소유권 RPC를 통해서만 가능하다. 기기 비밀/초대 코드/요청 제한 테이블은 authenticated REST에 조회 권한도 주지 않는다.
- 기기 토큰은 Supabase Auth JWT가 아니다. 학생은 service-only RPC를 직접 호출할 수 없고 Edge Function이 토큰 해시·승인·폐기를 확인한 뒤 자기 데이터만 처리한다.
- 참여 코드는 128비트 무작위, 해시 저장, 1시간 만료, 제한된 신청 횟수, 교사 승인, IP/전체 등록 속도 제한을 사용한다. 기기 등록은 256비트 비밀을 생성하여 해시만 서버에 저장한다.
- 교사 코드 발급/복구/정리 API는 실제 `auth.getUser()` 결과의 UUID와 active 교사 행과 개인 프로젝트 소유자(app_admins)를 모두 확인하고 owner_id가 같은 학급만 처리한다. service role이 RLS를 우회하므로 삭제·코드 발급 대상 목록을 서버가 제한한다. 최고 관리자도 다른 교사의 데이터를 보도록 우회하지 않는다. CORS를 인증으로 취급하지 않는다.
- 요청 본문은 스트림에서 크기를 제한하고 URL/UUID/ACK/이미지를 검증한다. 임의 URL fetch나 임의 SQL/테이블 중계 기능은 없다.
- 확장 UI 메시지의 발신자와 경로를 확인한다. 콘텐츠 스크립트는 동기화 요청만 보낼 수 있고 기기 비밀을 읽거나 일반 API를 중계하지 않는다. 저장소는 TRUSTED_CONTEXTS로 제한한다.
- 캡처는 private 버킷 + 완료된 업로드/소유 교사/만료 메타데이터 RLS + 인증 다운로드를 사용한다. 학생은 파일을 읽을 수 없고 업로드 경로도 서버가 명령의 학생/학급으로 정한다.
- 명령 ID·revision·만료·ACK로 중복·역전 적용을 제한한다. 실패·만료는 성공으로 바꾸지 않는다.

## 공개 저장소에 넣지 않는 값

서비스 비밀키/service_role, Google Client Secret, DB 비밀번호, 관리자 JWT, 학생 기기 비밀, 참여/비상 코드 원문, 실제 학생 명단/URL/이미지는 커밋하지 않는다. `.env*`를 무시하고 공개 `.env.example`만 제공한다. 빌드에는 프로젝트 설정을 넣지 않는다. 연결 폼/저장소 로딩에서 공개 키만 허용하고 service 역할/Secret을 거부한다. 브라우저 설정 검증만으로 비밀 유출을 막는다고 가정하지 않는다.

공개 프로젝트 URL과 publishable/anon 키는 공개 설정이다. 데이터 보호는 이 키를 숨기는 것이 아니라 Auth·RLS·기기 인증으로 강제한다.

## Git 이력 검사

이 작업 시작 시 `origin/main`의 `f847cf0b7f16eb447485e65bb1b4b0386df6b5f4`와 모든 로컬 참조가 가리키는 14개 Git blob을 점검했다. 개인키 헤더, GitHub 토큰 패턴, Supabase Secret 키, service_role JWT 패턴이 발견되지 않았다. 검사 출력에는 값이 아닌 파일·종류·행 번호만 사용했다. 이는 알려진 패턴의 정적 점검이며 외부 저장소의 삭제된 원격 참조나 모든 형태의 비밀까지 증명하는 것은 아니다.

기존 사용자의 Apps Script 자료는 참고용으로 읽었고 배포 주소·암호를 새 소스에 복사하지 않았다. 향후 실제 키를 공개 저장소에 넣었다면 단순 삭제로 해결하지 말고 해당 서비스에서 폐기·재발급해야 한다.

## 검증과 한계

로컬 PostgreSQL 엔진(PGlite)에서 익명/일반 사용자/관리자/service 역할, RLS, RPC 권한, 기기 간 ACK 위조 차단, private Storage 메타데이터 정책을 검사한다. Edge 입력·등록/승인/기록 HTTP 흐름도 검사한다. 실제 Supabase 호스팅의 Auth 서명·Realtime·Storage HTTP API 검증은 사용자 프로젝트 설정 후 추가해야 한다.

설치형 확장은 사용자가 소유한 Chrome 프로필 안에서 실행된다. 확장 소스나 로컬 저장소를 스스로 변조하는 기기를 신뢰할 수 있는 OS 잠금 장치로 취급하지 않는다. 학교의 관리 정책과 실제 크롬북 테스트가 필요하다. 오프라인 큐 한도, 휴면/유휴 시간 추정, 기기 분실 시 폐기 절차를 운영 전에 확인한다.

자동 예약 정리·실제 전체 삭제 UI·99대 동시 실환경 부하·제3자 침투 테스트는 완료하지 않았다.

## 이번 공격 시뮬레이션

[보안 검증 보고서](security-review.ko.md)에 재현·수정·잔여 위험을 구분했다. ④ SQL, 최신 device 함수, 학생 ZIP 1.1을 함께 적용한다. 공지는 웹사이트 DOM에 삽입하지 않고 확장 전용 창으로 옮겼다. Shadow DOM만으로는 브라우저 검색/선택을 막지 못함을 확인했으므로 보안 경계로 사용하지 않는다. 이미지 업로드 전에 만료 예약을 만들고 완료 전 Storage 읽기를 차단하며, 서버 업로드 확정 전 성공 ACK를 허용하지 않는다.

프로덕션 빌드에 CSP·no-referrer·초기 자원 무결성 정보를 넣고 프레임에서는 Auth 초기화 전에 실행을 중단한다. 호스팅 Supabase 표준 도메인만 연결하며 SDK 데이터 fetch는 캐시·리퍼러·리다이렉트를 제한한다. GitHub Actions 참조는 공식 태그에서 확인한 커밋으로 고정했다. 이 조치들은 신뢰한 자사 HTML/스크립트·배포 계정이 침해된 상황을 해결하지 않는다. 실제 Chromium에서 합성 토큰을 읽는 자사 스크립트 공격이 성공하는 잔여 위험을 재현했다.
