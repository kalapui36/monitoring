# 개인정보·공격 시뮬레이션 검증 보고서

검증일: 2026-11-04(한국 시간). 대상은 현재 작업 폴더의 개인 Supabase 방식 코드, 네 개의 SQL, Edge handler, 학생 확장과 프로덕션 빌드다. 실제 학생/계정/캡처는 사용하지 않았다. 소스가 아직 원격 배포된 상태라는 뜻은 아니다.

**판정: 재현한 문제를 보완했지만 ‘개인정보 문제가 절대로 발생하지 않는 구조’로 인증할 수 없다. 특히 공통 웹 배포 코드가 침해되거나 유효한 자격증명이 탈취되면 개인정보에 접근할 수 있다. 이 잔여 위험은 실제 로컬 브라우저에서 합성 토큰으로 재현했다.**

## 4. 실서비스 확인 결과와 범위 밖

문서에 기재된 기본 Pages 주소 `https://kalapui36.github.io/monitoring/`에 읽기 요청을 시도했지만, **클라우드 외부 접속 프록시가 CONNECT 403으로 차단**했다. 웹사이트가 403을 반환했다고 판정한 것이 아니며, 실제 게시 버전·응답 헤더·배포 상태는 확인하지 못했다. 제한을 우회하지 않았다.

사용자 Supabase 프로젝트/실제 로그인 권한도 연결되어 있지 않아 실제 RLS API·Storage 다운로드·OAuth·Realtime은 미검증이다. 이 보안 검증 시점에는 원격 push나 DB/사이트 배포를 하지 않았다. 후속 코드 반영은 DEPLOY.ko.md의 별도 배포 단계이며 이 보안 검사로 실서비스 검증을 대신하지 않는다. 학교 Chromebook에는 접속하지 않았고 실제 확장 설치·공지/잠금/캡처를 수행하지 않았다. 클라우드 Chromium의 확장 설치 정책을 우회하지 않는다.

## 5. 운영 전 필수 적용

1. 본인 Supabase에서 기존 DB를 백업한 뒤 SQL ①②③④를 순서대로 적용한다. 이전 단계가 끝났다면 새 ④를 적용한다. 보안 업데이트는 private 버킷 설정도 복구한다.
2. 최신 device Edge Function을 배포한다. 배포 실패를 무시하지 않는다.
3. 최신 웹을 빌드·게시한다. 웹은 ④의 보안 버전을 확인하지 못하면 데이터 화면을 열지 않는다.
4. 학생 ZIP 1.1을 적용하고 확장을 새로고침한다. 다른 폴더/확장 ID로 설치되면 재등록·승인이 필요할 수 있다. 실제 연결을 확인한다. 구형 확장/서버 조합은 명령을 수신하지 않아야 한다.
5. 실제 계정 두 개와 크롬북 한 대에서 [검증표](CHROMEOS.ko.md)를 수행한다. 다른 계정은 데이터/Storage 접근이 거부되고 소유자만 사용할 수 있어야 한다.

④ SQL은 버전 표식뿐 아니라 실제 함수/정책을 갱신한다. 보안 버전 숫자를 수동으로 올려 통과시키면 안 된다. 소프트웨어 버전 표식은 변조된 학생 기기의 무결성 증명이 아니다.

## 6. 남아 있는 개인정보 위험

- **공통 배포 코드·GitHub 계정·의존성 침해:** CSP가 허용하는 자사 코드가 세션 토큰/조회 데이터를 읽을 수 있다. CSP의 Supabase 연결 허용은 모든 개인 프로젝트를 지원하기 위한 것이므로 특정 교사의 프로젝트만 네트워크 허용하는 장치도 아니다. 초기 자원 SRI는 HTML 자체까지 변조할 수 있는 공격자를 막지 못한다.
- **Google/Supabase 계정·유효 토큰·service 키·교사 PC 침해:** 정상 권한으로 접근하면 RLS만으로 도난을 판별하지 못한다. 악성 확장/OS 침해/사회공학 공격은 제거하지 못했다.
- **허용된 기능으로 수집되는 민감 정보:** URL 경로/탭제목/캡처에는 개인정보가 들어갈 수 있다. query/fragment 제거와 시크릿 제외가 모든 개인정보를 판별·제거하지는 못한다. 교사 승인·학교 권한·안내·수집 중단이 필요하다.
- **보관·복사·운영 설정:** 자동 예약 삭제는 여전히 미설정이다. 만료 캡처는 조회를 막지만 물리 삭제는 정리 버튼이 필요하다. 로그·백업·이미 내려받은 파일과 과거 미추적 파일까지 자동 회수/삭제하지 않는다. 운영자가 private/RLS 정책을 다시 풀면 코드 밖의 노출 위험이 생긴다.
- **대량 요청과 기기 변조:** 기본 제한은 무료 사용량/가용성을 무조건 지키는 DDoS 방어가 아니다. 학생이 소스/로컬 저장소를 변조하면 화면 제어·보고의 진실성을 강제할 수 없으며 OS 전체 잠금 장치가 아니다.

개별 교사의 독립 도메인/검토된 자체 호스팅은 공통 배포 계정에 대한 의존을 줄일 수 있다. 별도 인증 중계·HttpOnly 쿠키는 토큰 직접 읽기를 줄일 수 있지만 침해된 웹이 사용자 권한으로 데이터를 읽는 위험까지 없애지는 못한다. 어느 쪽도 ‘절대 유출 불가능’이라고 표현해서는 안 된다.

## 7. 사고 의심 시

실제 비밀값을 채팅에 보내지 않는다. 프로젝트 SQL Editor에서 소유자 교사 회원의 active를 false로 설정하면 데이터 RLS/관리 API와 새 기기 수집을 차단할 수 있다. 필요하면 기기 등록도 폐기한다. OAuth/인증 세션·키 폐기는 노출 종류에 맞게 Supabase/Google의 절차로 수행한다. 이미 유출·복사된 데이터의 회수는 보장할 수 없고, 배포 코드 침해라면 서비스를 중단하고 신뢰할 수 있는 빌드로 복구해야 한다.
